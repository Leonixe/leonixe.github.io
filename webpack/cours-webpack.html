Introduction

Pourquoi
Webpack ?

Avant de toucher à la moindre ligne de config, il faut comprendre quel problème Webpack résout. Sinon, on utilise un outil sans savoir pourquoi — et on ne comprend rien quand ça casse.

Le problème du JavaScript "à l'ancienne"

Quand tu écris un site web, tu as un fichier HTML, un ou plusieurs CSS, et du JavaScript. Au début, ça ressemble à ça :

<script src="utils.js"></script>
<script src="api.js"></script>
<script src="components/header.js"></script>
<script src="components/nav.js"></script>
<script src="app.js"></script>

Le projet grossit. On se retrouve vite avec 15, 20 fichiers JS. Trois problèmes majeurs apparaissent :

🌐
Requête HTTP

Chaque fois que le navigateur télécharge un fichier (image, CSS, JS…), il fait une requête HTTP — une demande au serveur. Chaque requête prend du temps. 20 fichiers JS = 20 requêtes = chargement lent.

  • L'ordre des fichiers est critique : si app.js utilise une fonction de utils.js, il faut charger utils.js en premier. Un oubli et tout plante.
  • Les variables se polluent entre elles : toutes les variables JS déclarées dans les fichiers <script> partagent le même espace global. Un nom en double crée des bugs silencieux et difficiles à tracer.
  • Impossible d'utiliser les modules modernes : le système import/export de JavaScript moderne ne fonctionne pas de cette façon.

Ce que fait un bundler

📦
Bundler (en français : "empaqueteur")

Un bundler est un outil qui analyse tous tes fichiers JS, suit leurs dépendances, et les assemble en un ou plusieurs fichiers optimisés — qu'on appelle des bundles. Le navigateur ne télécharge plus qu'un seul fichier propre au lieu de 20.

Webpack est le bundler le plus utilisé dans l'industrie. Voici ce qu'il fait concrètement :

src/index.js ── importe ──→ utils.js
── importe ──→ header.js
── importe ──→ styles.css

Webpack analyse tout, résout les dépendances

└──→ dist/bundle.js ← 1 seul fichier optimisé ✅

Ce que Webpack apporte en plus

⚡

Performance

Il optimise le code pour que ton site charge le plus vite possible.

🔧

Compatibilité

Il transforme ton code moderne pour qu'il fonctionne sur les vieux navigateurs — on verra comment dans la section Loaders.

🎨

CSS & Assets

Il peut gérer non seulement le JS, mais aussi le CSS, les images et les fonts.

🔄

Dev Server

Il propose un serveur local qui recharge automatiquement le navigateur quand tu sauvegardes.

💡

En résumé : Webpack part d'un point d'entrée, suit toutes les dépendances (import), et produit un résultat propre et optimisé. On verra chacun de ces mécanismes dans les sections suivantes.

Les outils

NPM
& Yarn

Avant de pouvoir utiliser Webpack, il faut comprendre comment les outils s'installent dans un projet JavaScript. C'est là qu'on parle de npm et de Yarn — mais aussi de Node.js, qui est le fondement de tout ça.

Node.js — la base de tout

⚙️
Node.js

JavaScript a été inventé pour tourner dans le navigateur. Node.js permet de faire tourner du JavaScript en dehors du navigateur, directement sur ta machine ou un serveur. Webpack, npm, et tous les outils de développement web modernes tournent grâce à Node.js. C'est une installation obligatoire avant de commencer.

🏭

Imagine que JavaScript est un ouvrier qui ne peut normalement travailler qu'en usine (le navigateur). Node.js, c'est lui donner la possibilité de travailler aussi en atelier — sur ta machine, sans navigateur. Webpack est l'un de ces travaux d'atelier.

C'est quoi un gestionnaire de paquets ?

📦
Paquet (ou librairie)

Un paquet, c'est du code écrit par d'autres développeurs et mis à disposition gratuitement. Webpack, Babel, React, jQuery sont tous des paquets. Des millions sont disponibles sur npmjs.com, le registre public de JavaScript.

Un gestionnaire de paquets, c'est l'outil qui va chercher et installer ces paquets à ta place en une seule commande — sans que tu aies à télécharger des fichiers à la main.

📦

npm

Node Package Manager. Installé automatiquement avec Node.js. Le plus répandu, accède à npmjs.com qui héberge des millions de paquets.

🧶

Yarn

Alternative créée par Facebook. Plus rapide grâce à un système de cache avancé. Les deux font la même chose, avec une syntaxe légèrement différente.

Le fichier package.json — la carte d'identité du projet

C'est un fichier texte créé à la racine de ton projet. Il liste toutes les dépendances dont ton projet a besoin. Quand un collègue clone ton projet depuis GitHub, il n'a qu'à faire npm install : tout s'installe automatiquement depuis ce fichier.

{
  "name": "mon-projet",
  "version": "1.0.0",

  // Les commandes qu'on peut lancer avec : npm run <nom>
  "scripts": {
    "start": "webpack serve",
    "build": "webpack --mode production"
  },

  // Librairies dont TON APPLI a besoin pour fonctionner en ligne
  "dependencies": {
    "react": "^18.2.0"
  },

  // Outils dont TU AS BESOIN pour CONSTRUIRE l'appli (pas en prod)
  "devDependencies": {
    "webpack": "^5.88.0",
    "webpack-cli": "^5.1.0",
    "babel-loader": "^9.1.0"
  }
}
dependencies vs devDependencies

dependencies = ce dont ton appli a besoin pour tourner une fois mise en ligne (ex : React, une librairie d'animations). devDependencies = les outils dont tu as besoin pour construire l'appli (Webpack, Babel, ESLint…). Ces derniers ne seront pas installés quand ton appli est déployée en production : ça allège le déploiement.

Les numéros de version

Tu remarques le ^ devant les numéros de version, comme "webpack": "^5.88.0". Ça signifie "version 5.88.0 ou une version compatible plus récente". Le numéro suit un format à 3 chiffres : MAJEUR.MINEUR.CORRECTIF. Le ^ autorise les mises à jour mineures et correctifs, mais pas les changements majeurs (qui peuvent casser la compatibilité).

Les commandes essentielles

npm init -y
Crée un package.json vide dans le dossier
npm install
Installe toutes les dépendances listées dans package.json
npm install webpack --save-dev
Installe webpack en devDependency
npm install react --save
Installe react en dependency
npm run build
Lance le script "build" défini dans package.json
npm uninstall webpack
Désinstalle un paquet et le retire du package.json

npm vs Yarn — les équivalences

npmYarnCe que ça fait
npm installyarnInstalle toutes les dépendances
npm install webpack --save-devyarn add webpack --devAjoute un outil de dev
npm run buildyarn buildLance un script

Le fichier lock — pourquoi le commiter sur Git ?

Le package-lock.json (ou yarn.lock) enregistre les versions exactes de chaque paquet installé sur ta machine. Sans lui, ton collègue qui fait npm install demain pourrait obtenir des versions légèrement différentes — et des bugs impossibles à reproduire. Ce fichier garantit que tout le monde a exactement la même chose. Il doit toujours être commité sur Git.

✅

Conseil : Choisissez npm ou Yarn au début d'un projet et ne changez plus. Mélanger les deux crée deux fichiers lock incompatibles et des comportements imprévisibles.

Concept

Entry
& Output

Webpack a besoin de savoir deux choses fondamentales : d'où il part et où il doit déposer le résultat. Ce sont les propriétés entry et output.

Entry — le point de départ

🚪
Entry (point d'entrée)

C'est le premier fichier JS que Webpack va lire. À partir de là, il suit tous les import pour découvrir tous les fichiers dont ton projet a besoin — on appelle ça le graphe de dépendances. C'est comme partir d'une page d'un livre et suivre tous les liens pour retrouver tous les documents liés.

Output — le dossier de sortie

📤
Output (sortie)

C'est là où Webpack va écrire le résultat une fois tout assemblé. Par convention, dans un dossier dist/ (abréviation de distribution). C'est ce dossier qu'on envoie en production sur un serveur.

La config minimale

Toute la configuration Webpack se passe dans un fichier webpack.config.js à la racine du projet. Voici la version la plus simple possible :

// "path" est un module natif de Node.js pour manipuler les chemins de fichiers
const path = require('path');

module.exports = {

  // D'où Webpack part
  entry: './src/index.js',

  // Où Webpack dépose le résultat
  output: {
    filename: 'bundle.js',           // Nom du fichier généré
    path: path.resolve(__dirname, 'dist'), // Chemin absolu vers dist/
    clean: true,                    // Nettoie dist/ avant chaque build
  },

};

Pourquoi path.resolve() et pas juste "./dist" ?

Webpack exige un chemin absolu (par exemple /Users/romain/mon-projet/dist) et non un chemin relatif (comme ./dist). path.resolve(__dirname, 'dist') construit ce chemin complet de façon automatique, peu importe l'endroit où est installé le projet ou l'OS utilisé (Windows, Mac, Linux).

✅

Convention : On met toujours le code source dans src/ et le résultat généré dans dist/. Le dossier dist/ est toujours dans le .gitignore car il est généré automatiquement — on en reparlera dans la section dédiée.

Points d'entrée multiples

Pour des projets plus complexes (par exemple une partie publique et une partie admin séparées), on peut avoir plusieurs points d'entrée :

entry: {
  app: './src/app.js',       // Génèrera app.bundle.js
  admin: './src/admin.js',   // Génèrera admin.bundle.js
},
output: {
  filename: '[name].bundle.js', // [name] sera remplacé par "app" ou "admin"
  path: path.resolve(__dirname, 'dist'),
},
Concept

Loaders
& Babel

Par défaut, Webpack ne sait lire que le JavaScript. Les loaders lui permettent de comprendre d'autres types de fichiers : CSS, images, SCSS… Et c'est aussi ici qu'entre en jeu Babel, l'un des outils les plus importants de l'écosystème.

ES6 — c'est quoi ?

📜
ECMAScript (ES) — les versions de JavaScript

JavaScript suit une norme officielle appelée ECMAScript. Chaque année, une nouvelle version sort avec de nouvelles fonctionnalités. ES6 (sorti en 2015, aussi appelé ES2015) a été une révolution : il a introduit let, const, les fonctions fléchées (=>), les classes, import/export, et bien d'autres choses. Quand on dit "JavaScript moderne" ou "ES6+", on parle de cette version et celles qui ont suivi (ES7, ES8, ES2020, etc.).

Le problème de compatibilité navigateur

Le JavaScript moderne (ES6+) est pratique à écrire, mais les anciens navigateurs ne comprennent pas toute cette syntaxe. Un navigateur datant de 3-4 ans peut planter sur du code ES6 parfaitement valide.

🗣️

Imagine que tu écris un texte en français moderne avec des anglicismes courants. Un lecteur qui n'a appris le français qu'en 2010 ne comprendra pas certains mots. Babel, c'est le traducteur qui convertit ton français moderne en version compréhensible par tout le monde.

Babel — le transpileur

🔄
Transpilation

Transpiler = transformer du code source dans un langage vers du code source dans un autre langage (ou une autre version du même langage). Babel transpile ES6+ vers ES5 — la version de JavaScript comprise par tous les navigateurs, même les plus anciens.

// Ce que TU écris (ES6+) — moderne et lisible
const saluer = (nom) => `Bonjour ${nom} !`;

// Ce que BABEL génère (ES5) — compris par tous les navigateurs
var saluer = function(nom) {
  return 'Bonjour ' + nom + ' !';
};

Tu écris en ES6+ confortable, Babel s'occupe de la compatibilité. C'est le meilleur des deux mondes.

C'est quoi un loader ?

🔌
Loader

Un loader est un module qui enseigne à Webpack comment traiter un type de fichier précis. Sans loader CSS, Webpack ne sait pas quoi faire d'un fichier .css et plante. Avec le bon loader, il sait le lire, le transformer, et l'inclure dans le bundle.

📌

Règle de base : 1 type de fichier = 1 (ou plusieurs) loader(s). Quand plusieurs loaders sont listés, ils s'appliquent de droite à gauche dans le tableau use.

Les loaders les plus courants

LoaderRôle
babel-loaderPasse chaque fichier JS dans Babel pour transpiler ES6+ → ES5
css-loaderPermet à Webpack de lire et comprendre les fichiers CSS
style-loaderInjecte le CSS lu dans le DOM (le contenu visible de la page) via une balise <style>
sass-loaderCompile le SCSS (CSS avec des super-pouvoirs : variables, imbrication…) en CSS standard
file-loaderGère les images et les fonts — les copie dans dist/ et retourne leur chemin

Configuration dans webpack.config.js

module.exports = {
  module: {
    rules: [   // Un tableau de règles : une par type de fichier

      // Règle 1 : tous les fichiers .js passent par Babel
      {
        test: /\.js$/,         // Expression régulière : "fichier dont l'extension est .js"
        exclude: /node_modules/, // On n'essaie pas de transpiler les librairies tierces
        use: 'babel-loader',
      },

      // Règle 2 : les fichiers CSS
      {
        test: /\.css$/,
        // Ordre d'exécution : css-loader d'abord (droite), style-loader ensuite (gauche)
        use: ['style-loader', 'css-loader'],
      },

      // Règle 3 : les images (Webpack 5 — plus besoin de file-loader)
      {
        test: /\.(png|jpg|gif|svg)$/i,
        type: 'asset/resource',
      },

    ],
  },
};

Le fichier .babelrc — la config de Babel

Babel a besoin de sa propre configuration pour savoir quoi transpiler. On crée un fichier .babelrc à la racine :

{
  "presets": [
    ["@babel/preset-env", {
      // "Vise les navigateurs qui ont plus de 0.25% de parts de marché"
      "targets": "> 0.25%, not dead"
    }]
  ]
}
⚠️

Piège classique : style-loader injecte le CSS dans le DOM via du JavaScript (pratique en développement). Mais en production, on préfère un vrai fichier .css séparé pour de meilleures performances. C'est ce que fait MiniCssExtractPlugin — on en parle dans la section Plugins.

Concept

Les Plugins

Les loaders transforment des fichiers. Les plugins font tout le reste : ils interviennent sur l'ensemble du processus de build — générer un fichier HTML, extraire le CSS dans un vrai fichier, optimiser les images, etc.

🔧
Plugin

Un plugin est un module qui s'accroche au processus de build de Webpack pour effectuer des actions globales. Là où un loader ne peut traiter qu'un seul fichier à la fois, un plugin peut agir sur l'ensemble du bundle, créer des fichiers, injecter des variables, etc.

🏗️

Si les loaders sont les ouvriers spécialisés (le plaquiste, l'électricien…), les plugins sont le chef de chantier qui coordonne, génère les documents administratifs et s'assure que tout le bâtiment est cohérent.

Les plugins essentiels

🏗️

HtmlWebpackPlugin

Génère automatiquement un fichier index.html dans dist/ et y insère les balises <script> et <link> pointant vers tes bundles. Indispensable.

🎨

MiniCssExtractPlugin

Extrait tout le CSS dans un vrai fichier .css séparé, au lieu de l'injecter via JavaScript. À utiliser en production pour de meilleures performances.

🌍

DefinePlugin

Définit des variables globales accessibles partout dans le code (ex : savoir si on est en développement ou en production).

📉

BundleAnalyzerPlugin

Génère un rapport visuel de la taille de chaque morceau du bundle. Utile pour diagnostiquer pourquoi ton application est trop lourde.

Configuration

const HtmlWebpackPlugin = require('html-webpack-plugin');
const MiniCssExtractPlugin = require('mini-css-extract-plugin');

module.exports = {
  plugins: [

    // Génère dist/index.html basé sur notre template src/index.html
    new HtmlWebpackPlugin({
      template: './src/index.html',
    }),

    // Extrait le CSS dans un fichier séparé avec un hash dans le nom
    new MiniCssExtractPlugin({
      filename: '[name].[contenthash].css',
    }),

  ],
};

Le cache navigateur et le contenthash

🗄️
Cache navigateur

Pour aller plus vite, le navigateur mémorise les fichiers déjà téléchargés. Si tu revisites un site, il recharge les fichiers depuis sa mémoire plutôt que de les re-télécharger. Problème : si tu modifies ton CSS mais que le fichier s'appelle toujours style.css, le navigateur peut afficher l'ancienne version sans le savoir.

🔑
Hash & Cache Busting

Un hash est une empreinte numérique unique générée à partir du contenu d'un fichier. Si le contenu change, le hash change. En nommant les fichiers style.a3f9c2.css, on force le navigateur à télécharger la nouvelle version quand le hash change. C'est le cache busting ("contournement du cache").

Le [contenthash] dans le nom de fichier est automatiquement calculé par Webpack. Résultat : si ton CSS ne change pas, le navigateur garde sa version en cache. Si tu le modifies, le hash change → nouveau nom de fichier → le navigateur télécharge la nouvelle version.

✅

Différence loader / plugin : Si tu hésites entre les deux, pose-toi la question : "est-ce que ça concerne la transformation d'un type de fichier ou une action sur l'ensemble du build ?" Fichier → loader. Build entier → plugin.

Concept

Mode dev
& prod

La propriété mode dit à Webpack dans quel contexte il tourne. Selon la valeur, tout un ensemble de comportements change automatiquement. C'est l'un des concepts les plus importants pour avoir un workflow professionnel.

mode: "development" — pour coder

Build rapide, code lisible (non transformé), outils de débogage activés. On s'en fiche de la taille du fichier, on veut être productif.

mode: "production" — pour mettre en ligne

Build optimisé au maximum : code compressé, inutile supprimé. On veut que le site soit le plus rapide possible pour les utilisateurs.

Les optimisations du mode production

📉
Minification

La minification consiste à supprimer tout ce qui n'est pas nécessaire à l'exécution du code : les espaces, les retours à la ligne, les commentaires, et à raccourcir les noms de variables. Le code devient illisible pour un humain, mais le navigateur s'en fiche — il l'exécute pareil. Résultat : un fichier bien plus léger à télécharger.

// Avant minification (lisible, 180 octets)
function calculerTotal(prix, quantite) {
  const total = prix * quantite;
  return total;
}

// Après minification (illisible, 48 octets)
function c(a,b){return a*b}
🌳
Tree-shaking (littéralement : "secouer l'arbre")

Imagine une librairie de 500 fonctions dont tu n'utilises que 3. Le tree-shaking analyse statiquement tes import et supprime du bundle tout le code que tu n'utilises pas. C'est comme secouer un arbre pour ne garder que les fruits mûrs et laisser tomber les feuilles mortes (le code inutile).

// ❌ Mauvais pour le tree-shaking : importe TOUTE la librairie lodash
import _ from 'lodash';

// ✅ Bon : Webpack ne met dans le bundle QUE la fonction debounce
import { debounce } from 'lodash-es';

Les source maps — déboguer sans se perdre

🗺️
Source Map

Webpack transforme et regroupe tout ton code. Quand une erreur survient, le navigateur t'indique une ligne dans le fichier transformé — ce qui n'a aucun sens. Les source maps sont des fichiers qui font le lien entre le code transformé et ton code original. Avec elles, le navigateur t'affiche l'erreur dans ton vrai fichier, à la bonne ligne.

module.exports = {
  mode: 'development',
  devtool: 'source-map', // Active les source maps pour déboguer
};

Deux fichiers de config — une bonne pratique

En pratique, on sépare la configuration en deux fichiers pour ne pas faire de compromis entre vitesse de dev et optimisation de prod :

webpack.common.js ← config partagée (entry, output, loaders)
webpack.dev.js ← dev server, source maps, style-loader
webpack.prod.js ← MiniCssExtract, contenthash, minification 
{
  "scripts": {
    "start": "webpack serve --config webpack.dev.js",
    "build": "webpack --config webpack.prod.js"
  }
}

Première
config complète

On assemble tout ce qu'on vient de voir pour créer un projet de base fonctionnel, du npm init au premier build.

├── src/ ← ton code SOURCE (à versionner sur Git)

│ ├── index.html ← template HTML
│ └── styles/

Installation pas à pas

1

Crée le dossier et initialise le projet

mkdir mon-projet && cd mon-projet
npm init -y

→ Crée le fichier package.json avec des valeurs par défaut.

2

Installe Webpack et ses dépendances

npm install --save-dev \
  webpack webpack-cli \
  babel-loader @babel/core @babel/preset-env \
  css-loader style-loader \
  html-webpack-plugin

→ --save-dev : ces outils vont dans devDependencies car ils ne sont utiles qu'en développement.

3

Crée le fichier .babelrc

{
  "presets": ["@babel/preset-env"]
}
4

Crée webpack.config.js

const path = require('path');
const HtmlWebpackPlugin = require('html-webpack-plugin');

module.exports = {
  mode: 'development',
  entry: './src/index.js',
  output: {
    filename: 'bundle.js',
    path: path.resolve(__dirname, 'dist'),
    clean: true,
  },
  module: {
    rules: [
      { test: /\.js$/, exclude: /node_modules/, use: 'babel-loader' },
      { test: /\.css$/, use: ['style-loader', 'css-loader'] },
    ],
  },
  plugins: [
    new HtmlWebpackPlugin({ template: './src/index.html' }),
  ],
  devtool: 'source-map',
};
5

Lance le premier build

npx webpack

→ Vérifie que le dossier dist/ a été créé avec bundle.js et index.html dedans.

💡

npx webpack : le préfixe npx permet d'exécuter un outil installé dans node_modules sans l'installer globalement sur la machine. Une fois les scripts définis dans package.json, on utilisera npm run build à la place.

Aller plus loin

Dev Server
& HMR

Relancer npx webpack à chaque modification, c'est vite épuisant. Le webpack-dev-server surveille tes fichiers en permanence et recharge le navigateur automatiquement à chaque sauvegarde.

C'est quoi un serveur local ?

🖥️
Serveur local / localhost

Quand on développe, on ne peut pas simplement ouvrir un fichier HTML dans le navigateur — certaines fonctionnalités nécessitent un serveur. Un serveur local simule ce comportement sur ta machine. Il est accessible via l'adresse http://localhost:3000. localhost = ta propre machine. 3000 = le port, un numéro qui identifie l'application (comme un numéro d'appartement).

Installation & configuration

npm install --save-dev webpack-dev-server
module.exports = {
  // ... entry, output, module, plugins...
  devServer: {
    static: './dist',  // Le dossier à servir
    port: 3000,        // Accessible sur http://localhost:3000
    open: true,        // Ouvre le navigateur automatiquement au démarrage
    hot: true,         // Active le HMR (voir ci-dessous)
    compress: true,    // Compresse les fichiers envoyés au navigateur
  },
};
{
  "scripts": {
    "start": "webpack serve",          // Lance le dev server
    "build": "webpack --mode production"  // Build de production
  }
}

HMR — Hot Module Replacement

🔥
Hot Module Replacement (remplacement de module à chaud)

Sans HMR, chaque modification recharge toute la page — tu perds l'état de l'application (formulaires remplis, position de scroll, etc.). Avec HMR activé (hot: true), Webpack ne met à jour que le module qui a changé, sans recharger toute la page. Tu modifies ta couleur CSS → le navigateur se met à jour instantanément, sans perdre ce que tu avais à l'écran.

Une différence capitale à retenir

CommandeUsageCe qui se passe
npm startPendant le développementServeur local avec HMR, source maps, code non minifié. Aucun fichier écrit dans dist/
npm run buildAvant de mettre en productionBundle minifié, optimisé, tree-shaking. Les vrais fichiers sont écrits dans dist/
⚠️

Point important : Le dev server ne génère pas de fichiers dans dist/. Il fonctionne entièrement en mémoire pour être rapide. Pour obtenir les vrais fichiers à déployer, il faut toujours faire npm run build.

Bonne pratique

Le fichier
.gitignore

Tu as remarqué qu'on parle souvent de .gitignore. C'est un fichier texte simple mais absolument indispensable dans tous tes projets. Il dit à Git quels fichiers et dossiers il doit complètement ignorer.

Le problème sans .gitignore

Imagine que tu travailles sur un projet et tu fais git add . pour tout versionner. Sans .gitignore, tu enverrais sur GitHub :

node_modules/ — plusieurs centaines de Mo

Ce dossier contient toutes les librairies installées par npm. Il peut contenir des dizaines de milliers de fichiers et peser des centaines de Mo. Personne n'a besoin de le versionner car un simple npm install le recrée entièrement depuis le package.json.

dist/ — un dossier généré automatiquement

Ce dossier est produit par Webpack depuis ton code source. Il change à chaque build. Chaque développeur le recrée avec npm run build. Le versionner polluerait l'historique Git avec des changements sans valeur.

.env — informations confidentielles

Le fichier .env contient souvent des secrets : mots de passe de base de données, clés API (clés d'accès à des services payants comme Google Maps, Stripe, etc.). Les mettre sur GitHub, c'est les rendre publics — une grave faille de sécurité.

L'analogie

📬

Imagine que Git est un livreur de courrier. Tu lui prépares un colis avec ton code. Le .gitignore, c'est la liste des choses à NE PAS mettre dans le colis — les brouillons, les outils de travail, les documents confidentiels. Seul le contenu final et partageable va dans le colis.

Comment ça fonctionne ?

Le fichier .gitignore se place à la racine du projet. Chaque ligne contient le nom d'un fichier ou dossier à ignorer. Une fois listé, Git fait comme si ce fichier n'existait pas.

# Le dièse (#) sert à écrire des commentaires

# Dépendances npm — TOUJOURS ignorer
node_modules/

# Build Webpack — généré automatiquement
dist/

# Variables d'environnement — TOUJOURS ignorer (données sensibles !)
.env
.env.local
.env.production

# Fichier système créé automatiquement par macOS
.DS_Store

# Fichiers de log (journaux d'erreurs) générés automatiquement
*.log
npm-debug.log*
✏️
Syntaxe du .gitignore

dossier/ → ignore un dossier entier et tout son contenu.
*.log → le * est un joker : ignore tous les fichiers dont l'extension est .log.
# → commence un commentaire, la ligne est ignorée par Git.

⚠️

Piège classique : Si tu as déjà commité un fichier avant de l'ajouter au .gitignore, Git continuera à le suivre même après. Il faut alors le désindexer avec : git rm --cached nom-du-fichier. Cette commande retire le fichier du suivi de Git sans le supprimer de ta machine.

✅

Astuce : Le site gitignore.io génère un .gitignore adapté à tes technologies en quelques clics. Tape "Node", "Webpack", "macOS" et il produit un fichier complet automatiquement.

Laravel Mix
& alternatives

On a vu que configurer Webpack à la main demande du temps et de la rigueur. Des outils ont été créés pour simplifier ou même remplacer complètement cette configuration. Voici les principaux.

Le problème de la config Webpack "à la main"

Pour un projet standard — compiler du SCSS en CSS, transpiler l'ES6 avec Babel, gérer les images — on écrit facilement 50 à 80 lignes de configuration. C'est beaucoup pour un résultat qui est toujours le même. C'est là qu'interviennent les couches d'abstraction.

🏗️
Abstraction

Une abstraction cache la complexité pour exposer une interface plus simple. Tu décris ce que tu veux obtenir, l'outil se charge de comment y arriver. Laravel Mix est une abstraction de Webpack.

Laravel Mix

Laravel Mix est une surcouche de Webpack créée pour le framework PHP Laravel, mais utilisable dans n'importe quel projet. Elle remplace des dizaines de lignes de config Webpack par quelques lignes très lisibles.

Comparaison directe — même résultat, beaucoup moins de code

// ~60 lignes à écrire, comprendre et maintenir
module.exports = {
  entry: './src/js/app.js',
  output: { filename: 'app.js', path: resolve('public/js') },
  module: { rules: [
    { test: /\.js$/, use: 'babel-loader', exclude: /node_modules/ },
    { test: /\.scss$/, use: ['style-loader','css-loader','sass-loader'] },
  ]},
  plugins: [ new MiniCssExtractPlugin(...), new HtmlWebpackPlugin(...) ],
  // ... et ça continue
};
const mix = require('laravel-mix');

// 3 lignes. Babel, source maps, minification en prod : tout inclus.
mix.js('src/js/app.js', 'public/js')
   .sass('src/scss/app.scss', 'public/css');

Les méthodes Mix les plus utiles

MéthodeCe qu'elle fait
mix.js(src, dest)Bundle JS avec Babel automatiquement inclus
mix.sass(src, dest)Compile le SCSS en CSS (le SCSS est un CSS amélioré avec des variables, de l'imbrication...)
mix.css(src, dest)Traite du CSS standard via PostCSS
mix.copy(src, dest)Copie des fichiers statiques (images, fonts…)
mix.version()Ajoute un hash dans les noms de fichiers pour le cache busting
mix.browserSync()Recharge le navigateur automatiquement (comme HMR)
✅

Quand utiliser Mix ? Sur un projet Laravel ou WordPress, ou quand on veut être opérationnel vite sans se battre avec la config Webpack. C'est le bon choix pour la majorité des projets PHP.

Quiz

Quiz final

7 questions pour valider tout ce qu'on a vu ensemble. Bonne chance !

1. Qu'est-ce que Babel fait exactement dans un projet Webpack ?
🔴 Il regroupe tous les fichiers JS en un seul bundle
🟢 Il transforme le JavaScript ES6+ en ES5 pour que les anciens navigateurs comprennent le code
🔴 Il compresse les images pour réduire leur poids
✅ Correct ! Babel est un transpileur : il convertit la syntaxe JavaScript moderne (ES6+) vers une version plus ancienne (ES5) compatible avec tous les navigateurs.
2. Quelle est la différence entre dependencies et devDependencies dans le package.json ?
🔴 Il n'y a aucune différence, c'est juste une convention d'écriture
🟢 dependencies = nécessaires pour que l'appli tourne en ligne. devDependencies = outils de build uniquement, pas installés en production
🔴 devDependencies s'installe avec Yarn, dependencies avec npm
✅ Correct ! Webpack, Babel, ESLint → devDependencies. React ou une librairie utilisée dans l'appli → dependencies.
3. Dans la règle CSS use: ['style-loader', 'css-loader'], dans quel ordre les loaders s'appliquent-ils ?
🔴 style-loader en premier, puis css-loader
🟢 css-loader en premier (les loaders s'appliquent de droite à gauche), puis style-loader
🔴 L'ordre n'a aucune importance
✅ Correct ! Les loaders s'appliquent de droite à gauche. css-loader lit et interprète le CSS en premier, puis style-loader l'injecte dans le DOM de la page.
4. À quoi sert la minification du code en mode production ?
🔴 À rendre le code plus lisible pour les autres développeurs
🔴 À corriger les bugs automatiquement avant la mise en ligne
🟢 À supprimer les espaces, commentaires et raccourcir les noms pour réduire la taille du fichier
✅ Correct ! La minification rend le code illisible pour un humain mais beaucoup plus léger à télécharger pour le navigateur. Le code s'exécute exactement pareil.
5. Pourquoi met-on un hash (ex: style.a3f9c2.css) dans le nom des fichiers générés en production ?
🟢 Pour forcer le navigateur à télécharger la nouvelle version quand le contenu change, même s'il avait l'ancienne en cache
🔴 Pour rendre le nom de fichier plus sécurisé
🔴 Pour faciliter le débogage en production
✅ Correct ! C'est le cache busting. Le navigateur met les fichiers en cache pour aller plus vite. Changer le nom du fichier (via le hash) force le navigateur à re-télécharger la nouvelle version.
6. Pourquoi faut-il absolument mettre node_modules/ dans le .gitignore ?
🔴 Pour que le projet se charge plus vite sur GitHub
🟢 Parce qu'il est généré automatiquement par npm install, pèse des centaines de Mo, et chaque développeur peut le recréer lui-même
🔴 Pour cacher le code des librairies aux autres développeurs
✅ Correct ! node_modules/ est recrée depuis le package.json avec un simple npm install. Versionner ce dossier alourdirait inutilement le repo de plusieurs centaines de Mo.
7. Tu travailles sur un projet Laravel. Tu veux compiler du SCSS en CSS et bundler du JS sans écrire 60 lignes de config Webpack. Quel outil utilises-tu ?
🔴 Rollup, spécialisé dans les projets PHP
🔴 Parcel, car c'est le plus rapide et sans config
🟢 Laravel Mix, une surcouche de Webpack pensée pour l'écosystème Laravel
✅ Correct ! Laravel Mix configure Webpack automatiquement. Ce qui prend 60 lignes en Webpack brut s'écrit en 3 lignes avec Mix. C'est le choix naturel pour Laravel et WordPress.
